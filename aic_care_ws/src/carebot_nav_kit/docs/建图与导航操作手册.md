## 1. 上车前的准备（不占排队时间）

**这是最重要的一节。** 实验室机器人要排队，每一分钟都很贵。
下面这些事情**在你自己电脑上就能做完**，不要占用车时间。

### 1.1 编译验证（在你自己电脑上，用 Docker 或虚拟机装 ROS Kinetic）

```bash
# 把整包拷过去
cd ~/catkin_ws/src
cp -r /path/to/carebot_nav_kit .

# 只编译本包（不需要组委会的包）
catkin_make --pkg carebot_nav_kit
source devel/setup.bash

# 验证包被正确识别
rospack find carebot_nav_kit

# 校验 launch 文件（只解析、不启动任何节点）
roslaunch --nodes carebot_nav_kit bringup.launch
```

> ⚠️ **注意 `--dry-run` 是 ROS 2 的选项，ROS 1 没有。**
> ROS 1 里等价的用法是 **`roslaunch --nodes`** —— 它会完整解析 launch 文件
> （包括求值所有 `$(find ...)`、`$(arg ...)` 替换），但不启动节点。
> 语法错误、包缺失、参数引用错误都会在这一步暴露出来，**不需要机器人**。
>
> 相关选项：
> ```bash
> roslaunch --nodes  <pkg> <file>        # 列出会启动的节点
> roslaunch --files  <pkg> <file>        # 列出加载的所有文件（含 include 链）
> roslaunch --args=<节点名> <pkg> <file>  # 看某节点的最终命令行参数
> roslaunch --dump-params <pkg> <file>   # 导出所有参数
> ```

### 1.2 配置自检（完全离线，不需要 ROS）

```bash
cd carebot_nav_kit/scripts
python3 verify_nav_config.py
```

检查 22 项配置一致性。当前状态：**22 项全通过**。

### 1.3 先把点位草稿填好

`config/waypoints.yaml` 里的占位值先按赛题场地示意图估个大概，
上车后再用 `capture_pose` 服务精修。这样上车时只需要"微调"而不是"从零想"。

## 2. 硬件层检查

**上车后第一件事**，10 秒内排除"设备没插好"这类低级问题。

```bash
rosrun carebot_nav_kit check_hardware.sh
# 或直接
bash carebot_nav_kit/scripts/check_hardware.sh
```

它检查 7 类东西（**不需要 roscore**）：

| # | 检查项 | 说明 |
|---|---|---|
| 1 | 关键设备节点 | `/dev/stm32`、`/dev/carebot_laser_ls`、`/dev/fdilink_ahrs` 是否存在、权限对不对 |
| 2 | USB 设备 | 按 VID 找 CH340/CP210x/相机/麦克风阵列 |
| 3 | 串口占用 | **很隐蔽的故障源**：同一串口被两个进程打开会导致数据错乱 |
| 4 | udev 规则 | 设备名别名是否配置 |
| 5 | 用户权限 | 是否在 `dialout` 组 |
| 6 | ROS 环境 | `ROS_DISTRO` 是否设置 |
| 7 | 系统资源 | 内存/磁盘是否够 |

**典型输出（正常情况）**：

```
── 1. 关键设备节点
  [OK]   /dev/stm32                 STM32 底盘（实验室实车）  [777 root:dialout]
  [OK]   /dev/carebot_laser_ls      镭神 M10（实验室实车）    [777 root:dialout]
  [OK]   /dev/fdilink_ahrs          fdilink AHRS（实验室实车）[777 root:dialout]
```

**如果 `[失败]`**：先解决，别急着启动 ROS。上面的提示里有具体排查方向。

## 3. 软件层检查

硬件过了之后，启动底盘+雷达+IMU 底座，再检查软件层。

```bash
# 终端 1：启动底座
roslaunch carebot_nav_kit bringup.launch
```

`bringup.launch` 15 秒后会自动跑一次简版自检。看到 `move_base` 相关的警告是**正常的**
（底座阶段本来就没有 move_base）。

然后手动跑完整自检：

```bash
# 终端 2
rosrun carebot_nav_kit nav_check.py
```

检查 8 类（需要 roscore）：

| # | 检查项 | 关键点 |
|---|---|---|
| 1 | 核心话题 | `/scan_filtered` `/odom` `/tf` 是否存在 |
| 2 | 数据频率 | 雷达 ~10Hz、里程计 ~50Hz；**0 Hz 说明驱动崩了** |
| 3 | **激光健康度** | **最小测距必须 > 车体半径**，否则机器人把自己当障碍 |
| 4 | TF 链路 | `odom→base_footprint→base_link→laser_link` 是否连通 |
| 5 | 配置一致性 | 三处 `robot_radius` 是否一致 |
| 6 | 导航栈 | `amcl` / `move_base` / `/map`（底座阶段没有是正常的）|
| 7 | 运动测试 | 可选：`--motion-test` 实测底盘会不会动 |

### ⚠️ 第 3 项是最容易踩的坑

如果输出是这样：

```
[失败] 最小测距 < 车体半径     最小 0.052 m < 车体半径 0.180 m —— 雷达扫到了自己！
       → 把 laser_filter_chain.yaml 的 lower_threshold 提到 0.22 以上
```

**不要忽略它。** 这个问题的表现是"机器人原地打转不走路"：
costmap 把机器人自身标成障碍 → 全局规划器认为起点在障碍里 → 规划失败 →
恢复行为不停旋转。很多人会误以为是导航参数问题，查很久。

### 里程计健康度

**建图前**先让机器人静止 30 秒，观察有没有漂移：

```bash
rosrun carebot_nav_kit odom_monitor.py
```

正常输出：
```
[odom_monitor] 统计：49.8 Hz | 状态=still | 累计行进 0.00 m / 0.0° | 当前漂移 pos=0.0002 m yaw=0.0001 rad | 漂移告警 0 次
```

如果出现漂移告警：
- **IMU 零偏未标定** —— 静止时看 `/imu` 的角速度是否非零
- **刚启动就漂** —— 等 IMU 预热 30 秒再建图
- **EKF 误开了 roll/pitch** —— 检查 `ekf_params.yaml` 的 `imu0_config`

## 4. 建图完整流程

### 4.1 启动

```bash
# 终端 1
roslaunch carebot_nav_kit mapping.launch

# 终端 2（键盘遥控）
rosrun teleop_twist_keyboard teleop_twist_keyboard.py
```

### 4.2 遥控走场地的要领

**核心原则：慢。** gmapping 靠扫描匹配，走太快会跟丢。

| 操作 | 建议 |
|---|---|
| 速度 | 用键盘遥控的**最低档**（约 0.1~0.15 m/s） |
| 转弯 | **原地慢慢转**，不要边走边转 |
| 贴墙 | 沿墙走一圈，让雷达充分扫到墙面 |
| 门口 | **在门口多停 3~5 秒**，让雷达扫到门内 |
| 房间内部 | 每个房间走到**中心**并转一圈（360°） |
| 闭环 | **最后回到起点附近**，让 gmapping 闭合回路，能显著修正累积误差 |

**路线建议**（3m×3m 场地）：

```
起点 → 沿客厅外圈走一圈 → 进卧室走一圈 → 出来
     → 进厨房走一圈 → 出来 → 进书房走一圈 → 出来
     → 回到起点（闭环）
```

**不要在场地里放会动的东西**（人、椅子）。建图时人应该站在场地外，
否则会被永久建进地图变成"幽灵障碍"。

### 4.3 实时观察地图质量（rviz）

rviz 里重点看：

| 显示项 | 看什么 |
|---|---|
| `Map` | 墙体是否连续、有没有重影 |
| `LaserScan(filtered)` | 红点是否贴合墙面；**如果红点在机器人中心附近有一圈，说明滤波没生效** |
| `TF` | 打开看坐标轴是否都正常 |

**如果地图开始扭曲**（墙越来越歪）：
立刻停止移动 → 在 rviz 里看粒子/匹配是否还在工作 → 通常需要回到已知位置重新对齐。

### 4.4 保存地图

```bash
# 终端 3
rosrun carebot_nav_kit save_map.sh -n mymap
```

脚本会做 5 件事：
1. 检查 `/map` 是否有数据（防止保存空图）
2. 保存到临时目录并校验文件有效性
3. 修正 yaml 里的 `image:` 字段
4. 写入 `maps/mymap.{pgm,yaml}`（导航默认读取这里）
5. 在 `maps/history/` 留一份带时间戳的备份

## 5. 地图质量评估

保存后**必须**肉眼检查。用图像查看器打开 `maps/mymap.pgm`。

### 检查清单

- [ ] **墙体连续闭合**，没有断裂或缺口
- [ ] **没有大片黑斑** —— 那是把动态障碍/机器人自身建进去了
- [ ] **没有重影/双层墙** —— 那是里程计漂移导致的对不齐
- [ ] **三个房间门口是通的** —— 没被"堵死"
- [ ] **地图接近正方形** —— 3m×3m 场地应该是方的，如果是斜的说明有系统性角度误差

### 问题与对策

| 现象 | 原因 | 对策 |
|---|---|---|
| 重影 / 墙变双层 | 里程计漂移 | 跑 `odom_monitor.py`；标定 IMU；放慢建图速度 |
| 大片黑斑 | 建图时有人走动，或激光扫到自身 | 重新建图；确认 `laser_filter` 在跑 |
| 墙体断裂 | 走太快，扫描匹配跟不上 | 放慢速度重建 |
| 地图整体歪斜 | 雷达安装角或 IMU 航向有偏差 | 检查静态 TF 的 rpy；标定 IMU |
| 门口被堵 | 门框处扫描不充分 | 在门口多停几秒重建 |
| 地图是斜的平行四边形 | 角速度标定不准 | 跑 `calibrate_angular.py` |

## 6. 点位标定

地图 OK 之后标定点位。

### 6.1 启动导航

```bash
roslaunch carebot_nav_kit navigation.launch \
    map_file:=$(rospack find carebot_nav_kit)/maps/mymap.yaml
```

### 6.2 ⚠️ 给初始位姿（必做）

在 rviz 里：
1. 点顶部工具栏的 **"2D Pose Estimate"**
2. 在地图上机器人实际所在位置**按住鼠标左键拖出朝向**
3. 看 rviz 里的**粒子云**（红色箭头群）：
   - 散成一大片 → 位姿给错了，重给
   - 收敛成一小团 → 定位成功

### 6.3 标定每个点位

**方法（推荐）：用 capture_pose 服务**

```bash
# 用键盘遥控把机器人开到目标位置并对准朝向
rosrun teleop_twist_keyboard teleop_twist_keyboard.py

# 停下后，记录当前位姿到指定名字
rosservice call /nav/capture_pose "qr_area"
rosservice call /nav/capture_pose "point_A"
rosservice call /nav/capture_pose "room_B"
rosservice call /nav/capture_pose "room_C"
rosservice call /nav/capture_pose "room_D"
```

每次调用都会：
- 打印记录到的 `(x, y, yaw)`
- **自动写回** `config/waypoints.yaml`

**查看已标定的点位**：
```bash
rosservice call /nav/status_srv
```

### 6.4 ⚠️ 同步到任务状态机（容易漏！）

`carebot_eldercare` 用的是**另一份**点位文件：
`carebot_eldercare/config/waypoints.yaml`

标定完成后要把坐标同步过去，否则任务状态机还是会用占位值乱走。

或者改 `carebot_eldercare/launch/eldercare_full.launch`，
让 `mission_manager` 的 `waypoints_file` 参数指向 nav_kit 这一份：

```xml
<param name="waypoints_file"
       value="$(find carebot_nav_kit)/config/waypoints.yaml" />
```

**推荐后者**，只有一份点位文件，不会出现"改了一份忘了另一份"。

## 7. 导航验证

### 7.1 单点导航测试

```bash
# 用服务导航到命名点位
rosservice call /nav/goto "room_B"

# 或直接给坐标
rosservice call /nav/goto "1.5,0.8,0.0"
```

返回 JSON：
```json
{"ok": true, "name": "room_B", "attempts": 1, "elapsed": 8.4,
 "status": "reached", "message": "已到达",
 "target": {"x": 2.2, "y": 1.2, "yaw": 0.0}}
```

### 7.2 逐点验证

**每个点位至少跑 3 次**，且从不同起点出发（模拟赛题的随机起点）：

```bash
for i in 1 2 3; do
  for wp in qr_area point_A room_B room_C room_D; do
    echo "=== 第 $i 轮 $wp ==="
    rosservice call /nav/goto "$wp"
    sleep 3
  done
done
```

**验收标准**：
- 成功率达到 **90% 以上**
- 每个点位实际停靠位置与标定位置偏差 **< 10 cm**
- 没有"到了但朝向不对"的情况（朝向不对会影响后续的二维码/人脸识别）

### 7.3 用 rviz 观察导航过程

| 显示 | 正常表现 |
|---|---|
| `Global Plan`（绿线） | 从机器人到目标的一条连续路径 |
| `Local Plan`（橙线） | 贴合绿线，平滑 |
| `DWA Trajectories`（黄点簇） | 多条候选轨迹，选中的那条贴合路径 |
| `AMCL Particles` | 保持收敛的一小团，**不应该发散** |
| `Global/Local Costmap` | 障碍周围有代价梯度 |

**如果粒子云在导航中发散** → 定位跟丢了。检查里程计漂移、雷达是否被遮挡。

## 8. 速度标定

**如果发现"走得比指令远/近"或"转角不准"**，做标定。

### 8.1 线速度标定

```bash
# 前方留 2.5m
rosrun carebot_nav_kit calibrate_linear.py
```

按提示操作：机器人走 2m → 用卷尺量实际距离 → 输入 → 得到 `linear_scale`。

### 8.2 角速度标定

```bash
# 周围留 0.8m 空间，地面贴一条初始朝向标记
rosrun carebot_nav_kit calibrate_angular.py --turns 2
```

转 2 圈 → 观察实际朝向偏差 → 输入实际角度 → 得到 `angular_scale`。

### 8.3 应用系数

编辑 `config/robot/base.yaml`：
```yaml
calibration:
  linear_scale: 0.9604      # 填标定得到的值
  angular_scale: 1.0000
```

**改完重新标定验证一次**，误差应降到 ±2% 以内。

## 9. 常见问题与排查

### 9.1 机器人不动

```bash
# 1) 有没有速度指令
rostopic echo /cmd_vel

# 2) 里程计有没有更新
rostopic hz /odom

# 3) 串口在不在
ls -l /dev/stm32

# 4) 底盘是否因超时保护停车
#    STM32 底盘 1000ms 无指令会自动停电机 —— 正常现象
```

### 9.2 机器人原地打转不走路

**90% 是激光扫到了自己。**
```bash
rosrun carebot_nav_kit nav_check.py | grep -A2 "激光健康度"
```
把 `laser_filter_chain.yaml` 的 `lower_threshold` 提到车体半径 + 4cm 以上。

### 9.3 定位一直不收敛（粒子云散着）

| 原因 | 排查 |
|---|---|
| 初始位姿给错了 | 重新给 2D Pose Estimate |
| 地图与实际场地不符 | 确认加载的是当前场地的地图 |
| 雷达被遮挡/数据异常 | `rostopic hz /scan_filtered`；rviz 看红点 |
| AMCL 运动模型配错 | 确认 `odom_model_type` 是 `omni` |
| `laser_max_beams` 太少 | 调到 90 以上 |

### 9.4 导航能规划但走不到（中途停下）

| 现象 | 原因 | 对策 |
|---|---|---|
| 卡在门口 | 膨胀层太大，门过不去 | 减小 `inflation_radius`（但不要小于车体半径）|
| 路径贴墙 | `use_quadratic` 开着 | 设为 `false` |
| 反复前进后退 | DWA 振荡 | 调大 `oscillation_reset_dist`；减小 `path_distance_bias` |
| 目标点被判定在障碍里 | 点位标定偏了 | 重新标定该点位；或增大 `xy_goal_tolerance` |

### 9.5 `move_base` 报 "Timed out waiting for transform"

TF 链路有问题或系统负载过高：
```bash
rosrun tf view_frames      # 生成 frames.pdf，看树是否完整
```
调大 `transform_tolerance`（当前 1.0，可到 1.5）。

### 9.6 地图保存出来是空的

`map_saver` 在 `/map` 没数据时会生成空白图。
`save_map.sh` 已经做了检查，但如果绕过它直接用 `map_saver`，注意这一点。

## 10. 换硬件的操作

本包的设计目标之一是**换硬件只改参数、不改代码**。

### 10.1 用备选 profile

如果换成 Arduino 底盘 + ls01d 雷达 + art_imu：

```bash
roslaunch carebot_nav_kit mapping.launch \
    base_driver:=arduino \
    laser_driver:=ls01d \
    imu_driver:=art_imu
```

### 10.2 完整换一套（新增 profile）

复制 `config/hardware/alt_arduino.yaml` 改成新配置，然后在 launch 里指定。
配置项含义见文件内注释。

### 10.3 车体尺寸变了

改 `config/robot/base.yaml` 的 `geometry.radius`，
**同时**改 `config/nav/costmap_common_params.yaml` 的 `robot_radius`
（`verify_nav_config.py` 会检查这两处是否一致）。
